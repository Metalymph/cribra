# v0.7 Adapter Boundary Audit

> **Historical audit.** This document records the v0.7.0 boundary review. Its
> native ABI statement (protocol 0.1.0) is superseded by the published v0.7.2
> contract, which uses ABI **0.3.0**. See
> [Interoperability](INTEROP.md#17-abi-versioning) for the current protocol.

Date: 2026-10-15

## Scope

This audit reviews existing responsibility boundaries across the Rust core,
native C ABI, WebAssembly adapter, and CLI.

It does not require capability parity between adapters, introduce new
features, or propose architectural redesign.

Detailed native ABI compatibility, pointer ownership, error behavior,
and conformance remain subject to the separate Q9 gate.

## Rust core

Status: boundary consistent.

Evidence:

- `src/lib.rs` forbids unsafe code.
- The public API exposes whole-source scanning, streaming, incremental
  sessions, reports, queries, and review metadata.
- The `transform` feature gates transformation APIs.
- `parallel` and `serde` are optional Cargo features.
- Application I/O, networking, persistence, and UI remain outside
  the core responsibility boundary.

Documentation correction:

- The incremental-session API documentation incorrectly described
  v0.6.0 as unreleased. This was corrected without changing behavior.

## Native C ABI

Status: architectural boundary consistent.

Evidence:

- The adapter is implemented in `crates/cribra-capi`.
- The adapter explicitly enables core transformations.
- FFI-specific unsafe operations are isolated from the safe Rust core.
- The exported surface includes scanner construction, scanning,
  result traversal, explanations, transformations, and resource release.
- The public contract is documented in `docs/INTEROP.md` and
  `include/cribra.h`.

The C ABI does not promise exposure of every Rust API.

Detailed ABI and ownership verification is deferred to Q9.

## WebAssembly

Status: architectural boundary consistent.

Evidence:

- The adapter is implemented in `crates/cribra-wasm`.
- It uses `wasm-bindgen` directly rather than the C ABI.
- Its Core profile excludes transformations.
- Its Flow profile enables transformations and remains the default.
- The adapter forbids unsafe code.
- Streaming and incremental Rust sessions are not exposed as
  JavaScript APIs.

Core/Flow compilation and JavaScript runtime contracts were
qualified separately under Q1.

## CLI

Status: architectural boundary consistent.

Evidence:

- The CLI is implemented in `crates/cribra-cli`.
- It accepts one explicit UTF-8 file or standard input.
- It does not own repository traversal, glob expansion, or
  automatic directory discovery.
- Human and JSON outputs expose metadata rather than matched
  source values.
- The CLI has its own command and presentation contract.

Capabilities listed as gaps in `docs/CLI_PARITY.md` are CLI-specific
evolution candidates, not defects of the Rust core or prerequisites
for core v1.0.

## Findings

| Finding | Classification | Disposition |
| --- | --- | --- |
| Obsolete v0.6.0 release wording in `src/lib.rs` | Documentation drift | Corrected |
| Rust-only streaming and incremental APIs | Intentional adapter limitation | No action |
| CLI capability gaps | Independent adapter roadmap | No core action |
| C ABI unsafe boundary | Necessary FFI isolation | Detailed review in Q9 |

No architectural redesign or new core feature is justified by
this boundary audit.

## Conclusion

Q6 confirms that the existing adapter responsibilities remain
separate and coherent.

Adapter capability expansion does not automatically require a new
core minor release.

The remaining native ABI compatibility and ownership qualification
belongs to Q9.

## Q7 — Capability manifest decision

Decision: NOT JUSTIFIED for v0.7.

The current adapters do not require runtime capability negotiation.

- Rust capabilities are selected through Cargo features.
- WASM Core and Flow expose build-specific JavaScript APIs.
- The native C ABI exposes a documented header and ABI version functions.
- The CLI exposes its command contract through help and version output.

ABI version functions do not provide general capability discovery.
They are sufficient for the current versioning contract, not a
replacement for future feature negotiation.

A generalized manifest would duplicate existing build and interface
contracts without a demonstrated consumer requirement.

No implementation is scheduled. A future adapter may introduce
capability discovery independently if a concrete integration requires it.

## Q8 — Precompiled WASM distribution

Decision: APPROVED IN PRINCIPLE; DISTRIBUTION DEFERRED.

The repository already contains a production WASM packaging path:

- `make wasm-production` generates JavaScript, TypeScript declarations,
  optimized WASM, and an ESM package descriptor.
- `crates/cribra-wasm/tests/package/validate.mjs` validates the
  generated package structure.
- Rust/WASM semantic parity and runtime qualification have separate
  existing checks.
- The `Release WASM` workflow publishes the Rust crate to crates.io
  and creates a GitHub Release, but does not currently attach the
  precompiled JavaScript/WASM package.

The preferred future distribution is a versioned Flow-only archive
attached to the independent WASM adapter release.

Core remains buildable and qualified without requiring a separate
precompiled distribution. npm publication is not currently required.

Before enabling archive publication, the adapter release process must
verify the exact package contents, optimized artifact behavior,
version identity, and JavaScript/WASM loading contract.

This is adapter distribution work, not a Rust core capability gap.
It does not block core v0.7 or independently justify core v0.8.

## Q9 — C ABI compatibility and conformance

Decision: PASS WITH DOCUMENTATION CORRECTIONS.

Qualification evidence:

- 51 Rust C ABI tests passed.
- Clippy passed with warnings denied.
- The generated C header matched the committed header before corrections.
- The native C11 consumer smoke test passed.
- All 43 expected exported symbols were verified.
- Static library generation passed.
- Ownership, borrowed-view lifetimes, error handling, and panic
  containment were reviewed against existing implementation and tests.

Two documentation clarifications were identified:

1. Builder consumption occurs after output-pointer validation. A null
   `out_scanner` does not consume the builder.
2. Reusing an error-output slot requires releasing any previously owned
   error handle before the slot is cleared.

No ABI signatures, symbols, data layouts, ownership implementation, or
core behavior were changed.

The native ABI protocol remains independently versioned at 0.1.0.
